# Design

This is the working contract between services, and between the people and agents building them. The
requirements say *what*; this says *how the pieces meet*. If code and this document disagree, one of them has a
bug: fix it in a PR that edits this file first.

Infrastructure ports and credentials: `docs/operations.md`, "Local stack". Each service owns one database and
one login role; no service reads another's database or calls another service's HTTP API on a path a user is not
waiting for.

### Kafka consumer groups

`<service>` (e.g. `stays`, `booking`). One group per service, one subscription per topic it consumes. A consumer
ignores event types it does not handle; it does not fail on them, so adding an event to a topic is not a
breaking change for other consumers.

## Inside a service

```
src/Services/Stays/
  Viatica.Stays.Domain/          aggregates, value objects, domain rules. Kernel + OrionGuard only.
  Viatica.Stays.Application/     Features/<UseCase>/{Command|Query, Validator, Handler}.cs, IStaysDb,
                                 integration event handlers. EF Core (no provider), Relevox.Contracts.
  Viatica.Stays.Infrastructure/  StaysDbContext : IStaysDb, migrations, Kafka wiring, outbox/inbox mapping.
  Viatica.Stays.Api/             Program.cs, endpoint mapping per feature, the only project referencing Relevox.
```

- A use case is one folder: request record, OrionGuard validator, Relevox handler, and the endpoint mapping in
  the Api project's matching folder. No `Services/` grab bags, no generic repository.
- Commands load aggregates through `I<Service>Db` (tracked), call behaviour, save once. The outbox row for any
  integration event is added to the same `SaveChanges`.
- Queries project straight to response records with `AsNoTracking`, keyset paging through `Viatica.Kernel.Web`.
- Domain errors carry a code from the service's error list (below) and become the error envelope in the Api.
- Concurrency on aggregates: Postgres `xmin` as the row version, surfaced as `ETag`.
- Every host calls the Kernel.Web entry point, registers OpenTelemetry with one `ActivitySource` and one `Meter`
  named `Viatica.<Service>`, and exposes `/health/live` and `/health/ready`.
- Migrations run as a one-shot `migrate` command of the Api project in compose, never on startup.

## Identifiers and time

- Ids are UUID v7 (`Guid.CreateVersion7()`), generated by whoever creates the thing. Booking generates `TripId`,
  `ItemId`, `HoldId` and `PaymentId` before asking anyone to act, so every request is idempotent by id.
- Time comes from `TimeProvider`, injected. Instants are UTC `DateTimeOffset`; stay nights and rental days are
  `DateOnly` in the property's or location's local calendar.

## Quote tokens

Stays and Cars issue a quote token per quote: `base64url(json payload) + "." + base64url(HMAC-SHA256)`. The payload
is readable on purpose: Booking shows the item and the expected price from it without calling Stays. Booking
never trusts it: the owning service verifies the MAC (constant-time) and the expiry when it places the hold, and
the hold event carries the authoritative total. Payload fields:

```json
{ "v": 1, "kind": "stay", "propertyId": "...", "roomTypeId": "...", "checkIn": "2026-12-01",
  "checkOut": "2026-12-04", "quantity": 1, "total": { "amount": "936.00", "currency": "EUR" },
  "expiresAt": "2026-11-20T10:15:00Z" }
```

Cars use `"kind": "car"` with `locationId`, `categoryId`, `dropOffLocationId`, `pickUpAt`, `dropOffAt` and
`driverAge`: the price is for one driver, and a hold request for another age is refused as `QuoteInvalid`. Each
service has its own key; there is no shared quote key.

## Flight offers

Flight search results are offers cached in Valkey under a search id for the offer's lifetime. An offer joins a
trip only after `POST /flights/offers/{offerId}/price` (re-price) succeeded; Booking stores the re-priced offer id
and expected total. `FlightOrderCreated.Total` is authoritative.

## Personal data on the broker

Passenger details (names as in passport, date of birth, document) travel from Booking to Flights inside
`FlightOrderRequested.EncryptedPassengers`: AES-256-GCM, 12-byte random nonce, associated data
`"{tripId:N}:{itemId:N}"`, encoded `base64url(nonce || ciphertext || tag)`. The key is configuration
(`Viatica:Pii:PassengerKey`, 32 bytes base64), held only by Booking and Flights. A copied event replayed for
another trip fails authentication. Nothing else personal goes on Kafka: traveller ids, not names or emails.

## The checkout saga

Booking orchestrates; state lives on the `Trip` aggregate and its items. Every transition is caused by exactly
one event or command and is idempotent: replaying the cause in the target state is a no-op, recorded at debug.

### Trip states

```
Draft ──checkout──> Holding ──all held──> Authorizing ──authorised──> Ticketing ──all flights ticketed──> Committing
                       │                      │                          │                                 │
                       │ any rejected         │ declined                 │ refused                         │ all committed
                       v                      v                          v                                 v
                    Unwinding <───────────────┴──────────────────────────┘                             Capturing
                       │ everything released, voided                                                       │ captured
                       v                                                                                   v
                     Failed                                                                            Confirmed
```

- `Ticketing` is skipped when the trip has no flight; `Committing` when it has no stay or car.
- **Deadline.** On entering `Holding` the trip records `deadline = min(hold expiries, ticketing time limits) - 2
  minutes`, recomputed as holds and orders report back. A trip still before `Committing` at its deadline goes to
  `Unwinding` with `DeadlineReached`. A scheduled check in Booking drives this; it does not depend on any event
  arriving.
- **Unwinding** sends a release, void or void-request for every item that is held, ordered or authorised, and
  waits for each confirmation. Releases are idempotent at the owner, so an unwinding trip resends on restart.
- A late `PaymentAuthorized` for a trip already `Unwinding` or `Failed` is answered with `PaymentVoidRequested`.
  A late `FlightOrderCreated` with `FlightOrderVoidRequested`. A late hold with a release. Nothing is ever left
  held, ordered or authorised by a failed trip.

### Item states

| Kind | States |
|---|---|
| Stay, Car | `Pending -> Held -> Committed -> (Cancelled)`, or `Pending -> Rejected`, or `Held -> Released` / `Expired` |
| Flight | `Pending -> Ordered -> Ticketed -> (Cancelled)`, or `Pending -> Rejected`, or `Ordered -> Voided`, `Ticketed -> Voided` (unwinding inside the void window) |

A stay or car hold is committed whenever it is still `Held`, even past its `expiresAt`. Each service's expiry
sweeper is the only authority on expiry; a compare-and-set on the hold's status decides whether the commit or the
sweeper got there first. Until the sweeper runs the rooms or cars are still reserved, so a late commit oversells
nothing, and refusing it would make Booking unwind a trip whose flights are already ticketed.

### Payments

One payment per trip: authorise the sum of the authoritative item totals from the hold and order events, capture
the same amount on confirmation, refunds per cancellation. Payments answers every request with exactly one outcome
event per operation id, even when the provider timed out (it asks the provider for the outcome first).

## Invariants the system tests reconcile

After every system test, including chaos runs, these hold across all databases once the stack is quiet:

1. A `Confirmed` trip has a captured payment equal to the sum of its confirmed item totals; every stay and car item
   has a committed hold at the owner; every flight item has a ticketed order at the airline simulator.
2. A `Failed` trip has no captured payment, no authorisation left open, no committed or live hold, and no order at
   the airline simulator that is not voided.
3. For every stay room type and night, and every car category, location and day: `sold + held <= allotment`, and
   `sold` equals the quantity of committed, uncancelled holds covering it.
4. Every capture at the payment simulator belongs to a `Confirmed` trip; every refund to a cancelled item.
5. No outbox row older than 30 seconds, no inbox gap, DLQs empty (a chaos test that expects a DLQ entry says so).

## Events

`src/Contracts/Viatica.Contracts` is the catalogue: every record, its topic (`EventCatalog`) and its JSON
(snapshots under `tests/Viatica.Contracts.UnitTests/Snapshots`). Rules:

- Adding an optional field or a new event is fine. Renaming, removing or retyping a field is a breaking change:
  add a new record instead and keep consuming the old one until no producer sends it.
- Listing events (`StayListingUpdated`, `CarLocationUpdated`) are full snapshots with `ListingVersion`;
  availability events carry `AvailabilityVersion` per room type or category. Projections keep the highest version
  and drop the rest, so order across partitions does not matter.
- Every other event is keyed by trip and handled with the inbox, idempotently.
